Wait for an event

Goal: define the behavior of your first binary semaphore before implementing it. Sleep is complete by your report; now tasks need to coordinate work.

From time to events

Sleep waits for time to pass. An event wait lets A stop until B announces that something happened. A semaphore is a kernel object that connects that announcement to a waiting task. A task takes a token to proceed; another task gives a token to announce an event. A binary semaphore stores at most one available token.

If a token is available, take consumes it and returns. Otherwise the calling task becomes blocked: the scheduler excludes it until a give releases it. Its saved context is retained, just as with sleep. Unlike sleep, ticks do not release this wait.

Our first contract

  • Initially empty; one possible waiter; task callers only; no timeout.
  • Give with no waiter stores one token. Repeated gives still store only one.
  • Give with a waiter transfers the event to that waiter and makes it READY. The same event must not also remain as an available token.
  • Ready means eligible for scheduling, not necessarily executing immediately.

The check for an available token and registration as a waiter must form one protected operation. Otherwise a give can land between them and leave a task blocked despite an available event. We will use your interrupt-masking groundwork to reason through that interleaving before coding.

Prediction: the semaphore starts empty. B gives twice before A takes once. Does A block on its first take? Does it block on its second take if no further give occurs? Explain using the token count.
